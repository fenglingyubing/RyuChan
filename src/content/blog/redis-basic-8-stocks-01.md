# Java 面试专项：Redis 常见面试题总结（下）

> 参考来源：`八股文/Redis常见面试题总结(下)  JavaGuide.md`
> 整理目标：围绕 Redis 事务、性能优化、生产故障和缓存一致性提炼高频面试题，适合背诵和口头表达。

---
### 【面试题】：什么是 Redis 事务？它和 MySQL 事务有什么本质区别？
- **【核心答案】**：
  * Redis 事务本质上是把一组命令打包、排队，然后按顺序一次执行。
  * 它和关系型数据库事务不是一回事，不能简单套用 ACID 去理解。
  * Redis 事务在实际开发中用得很少，因为能力比较弱，而且很多场景用 `pipeline` 或 Lua 脚本更合适。
- **【原理解析】**：Redis 事务依赖 `MULTI` 和 `EXEC`。执行 `MULTI` 后，后续命令不会立即执行，而是先进入事务队列；执行 `EXEC` 时再按 FIFO 顺序依次执行。它的“事务性”更多体现为执行阶段不会被其他命令插入打断，但并不等价于数据库里的原子提交、失败回滚、持久化保证。Redis 官方也一直强调，事务设计目标是简洁和高性能，而不是完整的数据库事务语义。
- **【面试扩展】**：如果面试官问“那为什么还叫事务”，可以回答：因为它提供了命令分组和顺序提交能力，但本质更接近“批量顺序执行 + 简单隔离”，不是严格意义上的数据库事务。
- **【一句话总结】**：Redis 事务更像命令队列的顺序提交机制，而不是关系型数据库那种完整事务模型。

---
### 【面试题】：Redis 事务怎么用？`WATCH` 有什么作用？
- **【核心答案】**：
  * Redis 事务核心命令是 `MULTI`、`EXEC`、`DISCARD`、`WATCH`。
  * `MULTI` 开启事务、`EXEC` 提交执行、`DISCARD` 取消事务。
  * `WATCH` 本质上是乐观锁，用来监控一个或多个 key，若在提交前被其他客户端改动，事务就不会执行。
- **【原理解析】**：Redis 在 `MULTI` 之后只是把命令入队，并不会立刻执行。`WATCH` 的关键点在于“监控的是提交前是否被其他 Session 修改”。如果被监控的 key 在 `EXEC` 前被其他客户端改过，那么 Redis 会放弃整个事务，`EXEC` 返回空结果。它适合实现简单的 CAS 场景，比如余额扣减、库存检查这类“先读后判断再写”的轻量并发控制。
- **【面试扩展】**：容易踩坑的一点是：如果 `WATCH` 和事务在同一个 Session 中，事务内部自己去改被监控的 key，不会导致事务失败；只有“事务外部被其他客户端修改”才会触发 `WATCH` 失效。
- **【一句话总结】**：`WATCH` 就是 Redis 提供的乐观锁，拦的是“别人改过”，不是“自己事务里改过”。

---
### 【面试题】：Redis 事务支持原子性吗？为什么不支持回滚？
- **【核心答案】**：
  * 严格来说，Redis 事务不满足数据库事务要求的原子性。
  * 因为事务执行时如果某条命令运行出错，前面已执行成功的命令不会回滚，后面的命令该执行的仍可能继续执行。
  * Redis 不支持回滚，是为了保持实现简单、性能更高，也符合它“尽量在开发阶段发现错误”的设计哲学。
- **【原理解析】**：Redis 事务的错误分两类：入队阶段错误和执行阶段错误。入队阶段如果命令本身非法，`EXEC` 时整个事务不会执行；但如果是执行阶段出错，比如参数类型不匹配，那么出错命令之后的状态并不会自动恢复。由于 Redis 是内存数据库、单线程执行命令，如果引入回滚日志、补偿恢复、复杂状态管理，会显著增加系统复杂度和性能成本，这和 Redis 的设计目标相悖。
- **【面试扩展】**：这里很适合顺带说一句：很多人说“Redis 事务是原子操作”，这个说法只对了一半。更准确地说，它保证执行阶段不会被其他命令插队，但不能保证“要么全成功，要么全失败”。
- **【一句话总结】**：Redis 事务能保证顺序执行不被打断，但保证不了失败回滚意义上的原子性。

---
### 【面试题】：Redis 事务支持持久性吗？
- **【核心答案】**：
  * 也不能严格保证。
  * Redis 的持久化依赖 `RDB`、`AOF` 或混合持久化，而不是事务本身提供持久提交能力。
  * 即便使用 AOF，`appendfsync everysec` 和 `appendfsync no` 仍可能丢数据；`always` 虽然最安全，但性能太差，线上很少这么配。
- **【原理解析】**：数据库事务中的持久性强调“事务一旦提交，系统故障也不能丢”。Redis 的事务提交之后，数据是否真正安全落盘，取决于持久化策略是否已经把变更同步到磁盘。`RDB` 是周期快照，本身就有时间窗口；`AOF everysec` 最多可能丢 1 秒数据；`AOF no` 更依赖操作系统刷盘时机。因此 Redis 的事务不具备数据库事务那种强持久保障。
- **【面试扩展】**：如果被追问“那 Redis 为什么还适合做缓存”，可以答：因为缓存场景本来就不是强持久优先，而是高性能优先。真正的核心业务数据还是要落数据库，Redis 更多承接访问层压力。
- **【一句话总结】**：Redis 的持久性强弱取决于持久化策略，不取决于事务这层语义。

---
### 【面试题】：Redis 事务这么鸡肋，实际开发中一般怎么替代？
- **【核心答案】**：
  * 真实项目里更常用的是 Lua 脚本，而不是 Redis 事务。
  * Lua 脚本可以把多条命令一次发给 Redis 执行，减少网络开销，还能写简单逻辑。
  * 但 Lua 也不是数据库级原子事务，因为出错前已经执行的写操作同样不会回滚。
- **【原理解析】**：Lua 脚本在 Redis 中会被当作一条命令执行，执行期间不会被其他命令插入，因此很适合做“读 + 判断 + 写”这种需要连续性的操作，比如库存扣减、限流、分布式锁续约判断等。相比事务逐条命令入队、逐条网络交互，Lua 一次提交、在服务端执行，RTT 更低、逻辑更集中。不过它依旧不支持回滚，而且在 Cluster 模式下，如果脚本涉及多个不在同一哈希槽的 key，原子性也无法保证。
- **【面试扩展】**：可以顺手补一句：Redis 7.0 又引入了 `Redis Functions`，本质上是比 Lua 更工程化的可编程能力，但面试里大部分公司还是先问 Lua。
- **【一句话总结】**：Redis 里真正常用的“多命令原子执行”方案，通常不是事务，而是 Lua。

---
### 【面试题】：Redis 如何通过批量操作优化性能？原生批量命令、pipeline、Lua 有什么区别？
- **【核心答案】**：
  * Redis 性能优化里一个高频点就是减少网络往返，也就是减少 RTT。
  * 能批量就尽量批量：优先原生批量命令，其次 `pipeline`，需要顺序依赖和逻辑判断时用 Lua。
  * 三者都能减少网络开销，但能力边界完全不同。
- **【原理解析】**：一个 Redis 命令的总耗时不只有命令执行，还包括请求发送和结果返回，所以优化时不能只盯着 CPU，还要盯网络。原生批量命令如 `MGET`、`MSET` 是 Redis 原生支持的，语义最清晰；`pipeline` 是把多条命令一次性发出去，减少多次 socket I/O，但命令之间不具备原子性，也不适合前后依赖；Lua 则既能减少 RTT，又能在服务端写条件逻辑，并保证执行期间不被插队。
- **【面试扩展】**：如果在 Redis Cluster 下回答这题，要补充一句：无论是 `MGET`、`pipeline` 还是 Lua，若 key 分散在不同 hash slot，上述优化效果和原子语义都会打折，客户端通常要自己做路由和结果组装。
- **【一句话总结】**：批量优化 Redis 的核心，不是让命令更快，而是让网络往返更少。

---
### 【面试题】：什么是 bigkey？为什么 bigkey 很危险？
- **【核心答案】**：
  * bigkey 指 value 特别大的 key，比如 `String` 超过 `1MB`，或者复合类型元素数很多，比如超过 `5000` 个。
  * 它的危害不只是占内存，更会拖慢命令执行、放大网络传输、阻塞删除和迁移。
  * 线上遇到 bigkey，通常要尽快拆、删、限、异步释放。
- **【原理解析】**：Redis 是单线程执行核心命令的，操作 bigkey 时，无论是读取、删除还是迁移，都会占用主线程更长时间。读 bigkey 会导致网络包很大；删 bigkey 如果直接 `DEL`，释放内存可能阻塞主线程；主从同步、集群扩缩容时迁移 bigkey，也会让节点长时间卡顿。更麻烦的是，bigkey 容易和慢查询、热点问题叠加，最终把 Redis 从“高性能缓存”拖成“性能瓶颈点”。
- **【面试扩展】**：bigkey 的成因通常是设计不当，比如拿大对象、文件二进制、无上限集合直接塞 Redis，或者没有及时清理冗余字段。面试里可以顺带给出治理思路：拆分 key、换合适的数据结构、用 `UNLINK` 替代 `DEL`、打开 `lazy-free`。
- **【一句话总结】**：bigkey 最大的问题不是“大”，而是它会把 Redis 的单线程优势打没。

---
### 【面试题】：如何发现和治理 bigkey？
- **【核心答案】**：
  * 常见发现手段有 `redis-cli --bigkeys`、`SCAN` 配合长度命令、`MEMORY USAGE`、分析 RDB 文件，以及云厂商的 key 分析服务。
  * 治理上常见做法是拆分 bigkey、分批删除、异步删除、替换数据结构。
  * 线上操作要尽量避免一次性重操作，重点是“发现要轻、处理要稳”。
- **【原理解析】**：`--bigkeys` 能快速扫描出每类结构的代表性大 key，但它本身需要扫描全量 keyspace，对线上有一定影响；`SCAN` 更适合渐进式排查，结合 `STRLEN`、`HLEN`、`LLEN`、`SCARD`、`ZCARD` 等可以统计大小；Redis 4.0+ 还能用 `MEMORY USAGE` 直接看内存占用。真正处理时，优先拆分而不是硬删，因为一次性 `DEL` 大 key 很可能造成阻塞；需要删除时优先 `UNLINK`，把内存释放放到后台线程做。
- **【面试扩展】**：如果被问“为什么元素多不一定占内存大”，可以答：因为不同编码和元素内容长度不同，集合元素数量只是粗指标，不代表真实内存占用，所以最好结合 `MEMORY USAGE` 或 RDB 分析一起看。
- **【一句话总结】**：bigkey 治理的关键不是找到它，而是别用粗暴方式把 Redis 再打挂一次。

---
### 【面试题】：什么是 hotkey？它和 bigkey 有什么区别？
- **【核心答案】**：
  * hotkey 是访问频率异常高的 key，bigkey 是 value 特别大的 key，两者不是一回事。
  * hotkey 的核心风险是把 CPU、带宽或单分片流量打满，bigkey 的核心风险是单次操作代价太高。
  * 一个 key 既可能是 hotkey，也可能是 bigkey，这种组合最危险。
- **【原理解析】**：Redis 单实例、单线程处理请求，如果某个 key 的访问量远高于其他 key，那么这部分请求会集中命中同一个数据、同一个节点，造成热点倾斜。在 Cluster 模式下，这种问题更明显，因为一个热点 key 只能落在一个 hash slot 上，没法天然均摊到多个节点。和 bigkey 不同，hotkey 即使值很小，也可能因为 QPS 太高把实例打满；而 bigkey 即使访问不频繁，也可能因单次操作过重导致阻塞。
- **【面试扩展】**：业务里典型 hotkey 场景包括秒杀商品、热搜榜、爆款详情、突发新闻。治理时可以用读写分离、热点 key 打散、本地缓存、提前预热、限流降级等组合拳。
- **【一句话总结】**：bigkey 拼的是单次操作成本，hotkey 拼的是单位时间访问压力。

---
### 【面试题】：如何发现和处理 hotkey？
- **【核心答案】**：
  * 发现 hotkey 常用 `--hotkeys`、短时 `MONITOR`、业务埋点、开源工具和云服务分析。
  * `--hotkeys` 的前提是 Redis 开启 LFU 相关淘汰策略，否则拿不到访问频率统计。
  * 处理 hotkey 常见办法是读写分离、集群分摊、热点打散、多级缓存、限流降级和提前预热。
- **【原理解析】**：`--hotkeys` 的底层依赖 LFU 统计信息，所以只有 `volatile-lfu` 或 `allkeys-lfu` 等策略开启时才有意义；`MONITOR` 虽然最直观，但它会实时输出所有命令，对线上性能影响很大，只适合短时应急排查。真正治理时，重点是把请求从单点上摊开：可以把热点 key 复制成多个子 key 做随机读，也可以在 JVM 本地加一级缓存，或者把读流量切给从节点。若热点来自突发流量，还要配合限流、熔断和降级保护数据库。
- **【面试扩展】**：回答时可以补一个工程细节：热点打散适合读多写少场景，如果写频繁，会引入多副本一致性维护成本，所以不要把“打散”当成万能药。
- **【一句话总结】**：hotkey 的治理本质，就是把集中流量拆散、削峰、前移。

### 【面试题】：Redis 慢查询是怎么回事？怎么排查？
- **【核心答案】**：
  * Redis 慢查询指的是“命令执行阶段”耗时过长，不包括网络往返时间。
  * 常见元凶是高时间复杂度命令，比如 `KEYS *`、`HGETALL`、`SMEMBERS`，以及返回结果过大的范围查询。
  * 排查主要靠 `Slow Log`，核心命令有 `SLOWLOG GET`、`SLOWLOG LEN`、`SLOWLOG RESET`。
- **【原理解析】**：Redis 把一次请求拆成发送命令、命令排队、命令执行、返回结果四步，慢查询只统计第 3 步。之所以要强调这点，是因为很多线上“变慢”并不一定是命令本身慢，也可能是网络、排队或阻塞问题。`slowlog-log-slower-than` 可以设置阈值，单位是微秒；超过阈值的命令会被记录到内存中的慢日志里，日志条目会包含耗时、命令内容、时间戳和客户端来源，便于回溯定位。
- **【面试扩展】**：如果面试官追问“是不是 O(n) 命令就绝对不能用”，你可以答：不是，关键是 N 的规模是否可控。真有遍历需求时，尽量用 `SCAN`、`HSCAN`、`SSCAN`、`ZSCAN` 替代全量遍历命令。
- **【一句话总结】**：Redis 慢查询排查的第一步，不是猜，而是先看 `SLOWLOG`。

---
### 【面试题】：什么是缓存穿透？怎么解决？
- **【核心答案】**：
  * 缓存穿透指请求的 key 既不在缓存里，也不在数据库里，导致请求每次都直接打到数据库。
  * 它常见于恶意攻击、参数非法、业务边界值没处理好。
  * 常见解决方案是参数校验、缓存空值、布隆过滤器、接口限流。
- **【原理解析】**：缓存穿透的问题不在“缓存失效”，而在“请求目标本来就不存在”。因此如果每次都让它穿透到 DB，相当于 Redis 完全失去保护作用。缓存空值是最简单的办法，但只能拦住重复访问同一无效 key 的情况；如果攻击者每次构造不同 key，空值缓存效果有限。布隆过滤器更适合这种场景，它能用很低的空间成本做“是否可能存在”的前置过滤，把明显不可能存在的请求挡在缓存层外。
- **【面试扩展】**：回答时最好加一句取舍：布隆过滤器有误判，不会漏判，所以适合做“预过滤”，但不能替代数据库真查；缓存空值要设置较短 TTL，否则容易积压大量无效数据。
- **【一句话总结】**：缓存穿透的本质是请求打的根本不是“缓存失效数据”，而是“压根不存在的数据”。

---
### 【面试题】：什么是缓存击穿？它和缓存穿透有什么区别？
- **【核心答案】**：
  * 缓存击穿指某个热点 key 在数据库中存在，但缓存里恰好失效了，导致大量并发请求同时打到数据库。
  * 它和缓存穿透的区别在于：击穿查的是“真实存在的数据”，穿透查的是“根本不存在的数据”。
  * 解决思路一般是热点永不过期或长 TTL、提前预热、加互斥锁重建缓存。
- **【原理解析】**：缓存击穿的核心在“热点 + 失效 + 并发”。一个普通 key 过期了问题不大，但如果是高并发热点 key，比如秒杀商品详情，一旦失效，瞬时流量会全部绕过 Redis 砸到数据库。这时最关键的是控制“谁去回源”，否则会形成数据库惊群。常用方式是只有一个线程拿锁回源重建缓存，其他线程等待或快速失败。
- **【面试扩展】**：击穿和 hotkey 经常同时出现，所以很多方案会一起用：提前预热热点数据、把过期时间设置得覆盖活动周期、在极端场景下用逻辑过期 + 异步刷新，避免真实过期带来的流量尖刺。
- **【一句话总结】**：缓存击穿不是缓存里没数据，而是热点数据在最不该失效的时候失效了。

---
### 【面试题】：什么是缓存雪崩？怎么做系统级防护？
- **【核心答案】**：
  * 缓存雪崩指大量缓存同一时间失效，或者整个 Redis 服务不可用，导致海量请求同时落到数据库。
  * 它是“面”上的问题，击穿更像“点”上的问题。
  * 常见防护手段有 Redis 集群、多级缓存、过期时间随机化、热点预热、限流降级。
- **【原理解析】**：缓存雪崩的可怕之处在于它不是单个热点导致，而是大量 key 或整个缓存层一起失去保护能力。若原因是批量 key 同时过期，就要从 TTL 设计入手，把过期时间随机打散；若原因是 Redis 整体宕机，就要靠高可用集群、本地缓存兜底和熔断限流来保护数据库。很多系统在雪崩时真正挂掉的不是 Redis，而是被透传流量冲垮的数据库。
- **【面试扩展】**：缓存预热也是常见追问，标准回答一般是两种：定时任务主动把热点数据灌入缓存，或者通过消息队列异步触发缓存加载。前者简单，后者更灵活也更适合事件驱动系统。
- **【一句话总结】**：缓存雪崩本质上是缓存层整体失守，考验的是系统级防线而不是单点技巧。

### 【面试题】：如何保证缓存和数据库的数据一致性？
- **【核心答案】**：
  * 绝对强一致很难，工程上追求的是“最终一致 + 性能可接受”。
  * 最常见方案是 `Cache Aside Pattern`：读时先查缓存，没命中再查库并回填；写时先更新数据库，再删除缓存。
  * 如果更新数据库成功但删除缓存失败，通常通过重试机制或消息队列异步补偿来解决。
- **【原理解析】**：缓存和数据库是两套存储，只要不是单系统内原子提交，就必然存在短暂不一致窗口。`Cache Aside` 之所以常见，是因为它把缓存当成数据库旁路层：读路径由缓存兜底，写路径则以数据库为准，再通过删除缓存让后续读取自然回源。相比“先更新缓存再更新数据库”，这种做法更稳，因为缓存天生允许短暂过期、不一致，而数据库不能乱。真正难点在于“删缓存失败怎么办”，这时就要靠 TTL 缩短脏数据存活时间，或者更常见地引入消息队列做异步重试直到删除成功。
- **【面试扩展】**：如果面试官继续追问“双删策略、延迟双删值不值得用”，你可以答：有一定效果，但本质还是经验型补丁，真正稳妥的是把失败路径纳入重试和补偿体系，而不是指望一次操作绝对成功。
- **【一句话总结】**：缓存一致性没有银弹，主流思路是数据库为准、缓存做旁路、失败靠补偿。

### 【面试题】：哪些情况会导致 Redis 阻塞？线上怎么规避？
- **【核心答案】**：
  * Redis 阻塞不只来自慢命令，还可能来自持久化、刷盘、大 key 删除、集群迁移、Swap、CPU 抢占和网络问题。
  * 常见高风险点包括 `KEYS *`、`HGETALL`、`SMEMBERS`、`SAVE`、大 key 的 `DEL`、`FLUSHALL`、AOF `fsync`、扩缩容迁移。
  * 规避思路就是少做重操作、把能异步的异步掉、把能分批的分批做、把能监控的监控起来。
- **【原理解析】**：Redis 主线程一旦被长时间占住，请求就只能排队，表现出来就是 RT 飙升、超时、吞吐下降。O(n) 命令会直接拉长执行时间；`SAVE` 会同步阻塞主线程；AOF 写日志和刷盘在磁盘压力大时也可能间接卡住主线程；大 key 删除和数据迁移会把 CPU、内存释放和网络三种成本叠加；系统层面如果发生 Swap 或 CPU 被其他进程抢占，Redis 即使命令本身不慢，也会整体变卡。
- **【面试扩展】**：这题很适合落到使用规范上：避免全量遍历命令，遍历用 `SCAN`；删除大 key 用 `UNLINK`；快照优先 `BGSAVE`；不要长时间开 `MONITOR`；控制 key 生命周期；集群迁移提前评估 bigkey 和窗口期。
- **【一句话总结】**：Redis 阻塞的本质就是主线程被占住，所有优化最终都是在保护主线程空出来处理请求。
