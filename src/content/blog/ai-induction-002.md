# Java 集合常见面试题总结（下）

> 参考来源：JavaGuide《Java集合常见面试题总结(下)》
> 整理目标：提炼为适合面试表达的 Java 集合专项八股文。

---
### 【面试题】：`HashMap` 和 `Hashtable` 有什么区别？
- **【核心答案】**：
  * `HashMap` 线程不安全，`Hashtable` 线程安全，但 `Hashtable` 基本已经被淘汰。
  * `HashMap` 允许 `null key` 和 `null value`，`Hashtable` 不允许，传入会抛 `NullPointerException`。
  * `HashMap` 默认初始容量是 `16`，扩容为 `2` 倍；`Hashtable` 默认初始容量是 `11`，扩容为 `2n+1`。
  * JDK 1.8 之后 `HashMap` 在高冲突场景下会树化，`Hashtable` 仍然主要是数组加链表。
- **【原理解析】**：`Hashtable` 通过大量 `synchronized` 方法保证线程安全，本质上是整表级别的粗粒度同步，读写容易互相阻塞。`HashMap` 追求单线程场景下的高性能，通过扰动函数、位运算定位桶位、链表转红黑树等机制优化访问效率。JDK 1.8 中，当链表长度超过 `8` 且数组长度至少为 `64` 时，`HashMap` 会把链表转为红黑树，把最坏查找复杂度从 `O(n)` 降到 `O(log n)`。
- **【面试扩展】**：生产环境如果需要线程安全的哈希表，标准答案通常是 `ConcurrentHashMap`，而不是 `Hashtable`。如果面试官追问“为什么 `HashMap` 容量是 2 的幂”，可以继续回答位运算取模和扩容迁移优化。
- **【一句话总结】**：`HashMap` 是高性能的非线程安全哈希表，`Hashtable` 是历史遗留的粗粒度同步哈希表。

### 【面试题】：`HashMap` 和 `HashSet` 有什么区别？
- **【核心答案】**：
  * `HashMap` 实现 `Map` 接口，存储的是键值对。
  * `HashSet` 实现 `Set` 接口，只关心元素本身，不单独保存业务 value。
  * `HashSet` 底层本质上就是基于 `HashMap` 实现的。
- **【原理解析】**：`HashSet` 内部维护了一个 `HashMap`，把集合元素当成 `HashMap` 的 key，把一个固定占位对象当成 value。调用 `add(e)` 时，本质上是在执行 `map.put(e, PRESENT)`。因此，`HashSet` 的去重能力不是自己单独实现的，而是来自 `HashMap` 对 key 唯一性的约束。
- **【面试扩展】**：如果对象没有正确重写 `hashCode()` 和 `equals()`，`HashSet` 的去重就会失效或表现异常。开发中如果只需要判重、不关心 value，优先考虑 `Set`，语义更清晰。
- **【一句话总结】**：`HashSet` 可以理解成“只用 key、不关心 value 的 `HashMap`”。

### 【面试题】：`HashMap` 和 `TreeMap` 的区别是什么？
- **【核心答案】**：
  * `HashMap` 适合无序场景下的快速存取，平均时间复杂度通常是 `O(1)`。
  * `TreeMap` 适合按 key 排序和范围查询，核心操作复杂度是 `O(log n)`。
  * `HashMap` 底层是数组加链表/红黑树，`TreeMap` 底层是红黑树。
- **【原理解析】**：`TreeMap` 实现了 `SortedMap` 和 `NavigableMap`，不仅能按 key 自动排序，还支持 `floorEntry()`、`ceilingEntry()`、`subMap()`、`headMap()`、`tailMap()` 等导航和范围查询能力。这些能力依赖红黑树的自平衡特性，保证插入、删除、查找都维持在 `O(log n)`。而 `HashMap` 更关注散列分布和桶定位，不保证有序性。
- **【面试扩展】**：如果 key 不具备可比性，且没有传入 `Comparator`，`TreeMap` 在插入时会抛异常。业务里需要“按时间范围查数据”“查最接近某个 key 的记录”时，`TreeMap` 比 `HashMap` 更合适。
- **【一句话总结】**：`HashMap` 强在快，`TreeMap` 强在有序和范围查询。

### 【面试题】：`HashSet` 是怎么判断元素重复的？
- **【核心答案】**：
  * 先比较 `hashCode()`，哈希值不同，通常直接认为不是同一个元素。
  * 如果哈希值相同，再调用 `equals()` 判断对象逻辑上是否相等。
  * 只有 `hashCode()` 相同且 `equals()` 返回 `true`，才会被判定为重复。
- **【原理解析】**：`HashSet` 调用底层 `HashMap#put()` 时，会先根据哈希值定位桶位。若桶位为空，直接插入；若桶位已有元素，就继续比较 hash 和 key 的相等性。因为不同对象可能产生相同哈希值，所以哈希冲突后必须再通过 `equals()` 做最终确认。这也是为什么 Java 规范要求：重写 `equals()` 时通常必须同时重写 `hashCode()`。
- **【面试扩展】**：只重写 `equals()` 不重写 `hashCode()`，会导致逻辑上相等的对象被放到不同桶里，`HashSet` 无法正确去重。这类问题在实体类、DTO、权限对象中非常常见。
- **【一句话总结】**：`HashSet` 去重的本质是“先比哈希，再比等价性”。

### 【面试题】：`HashMap` 的底层实现是什么？JDK 1.7 和 JDK 1.8 有什么区别？
- **【核心答案】**：
  * JDK 1.7 的 `HashMap` 是数组加链表。
  * JDK 1.8 的 `HashMap` 是数组加链表加红黑树。
  * JDK 1.8 中链表长度超过 `8` 且数组长度至少为 `64` 时，才会树化，否则优先扩容。
- **【原理解析】**：`HashMap` 会先通过 `hash(key)` 对原始哈希值做扰动，再通过 `(n - 1) & hash` 计算桶下标。JDK 1.7 冲突主要靠链表解决，链表一长，查找复杂度会退化到 `O(n)`。JDK 1.8 引入红黑树后，在高冲突场景下可以把查找复杂度优化到 `O(log n)`。但树化并不是无条件发生，因为数组较小时，优先扩容能更低成本地把元素重新打散。
- **【面试扩展】**：常见追问有三个：为什么扰动函数只右移 `16` 位、为什么阈值是 `8`、为什么最小树化容量是 `64`。这些都和性能折中、泊松分布概率以及扩容成本有关。
- **【一句话总结】**：`HashMap` 本质是哈希桶结构，JDK 1.8 用红黑树优化了极端冲突场景。

### 【面试题】：`HashMap` 的长度为什么通常设计成 2 的幂次方？
- **【核心答案】**：
  * 因为可以把 `%` 取模优化成 `&` 位运算，计算更快。
  * 更容易让哈希值分布均匀，减少桶冲突。
  * 扩容后元素迁移规则更简单，只看某一高位是 `0` 还是 `1`。
- **【原理解析】**：当数组长度是 `2^n` 时，`hash % length` 等价于 `hash & (length - 1)`。位运算效率高于取模，而且 `length - 1` 的二进制会形成连续的低位 `1`，能更充分利用扰动后的低位信息。扩容为 2 倍时，元素的新位置只有两种可能：要么保持原索引不变，要么移动到“原索引 + 旧容量”，迁移逻辑简单，且整体分布更均匀。
- **【面试扩展】**：如果容量不是 2 的幂，可能导致某些二进制位永远参与不到寻址，哈希分布会变差。业务里如果能预估元素数量，初始化时指定接近目标量的容量，可以减少扩容次数。
- **【一句话总结】**：容量取 2 的幂，本质上是为了让寻址更快、分布更均匀、扩容更省事。

### 【面试题】：`HashMap` 在多线程下为什么可能出现死循环问题？
- **【核心答案】**：
  * 这个问题主要出现在 JDK 1.7 及之前版本。
  * 并发扩容时，头插法迁移链表可能把节点指针改乱，最终形成环形链表。
  * 一旦链表成环，后续 `get()` 遍历链表时就可能死循环。
- **【原理解析】**：JDK 1.7 的 `HashMap` 在 `resize()` 迁移元素时采用头插法，新节点会插到链表头部。如果多个线程同时迁移同一条链表，节点的 `next` 指针可能被交叉覆盖，最后生成闭环。JDK 1.8 改成了更安全的迁移方式，解决了“扩容成环”问题，但并没有让 `HashMap` 具备线程安全性。
- **【面试扩展】**：回答这题时要避免一个常见误区：JDK 1.8 只是修复了并发扩容导致的死循环问题，不代表 `HashMap` 可以在并发写场景下安全使用。并发场景仍应选择 `ConcurrentHashMap`。
- **【一句话总结】**：JDK 1.7 `HashMap` 的死循环，本质上是并发扩容时链表重连出错导致成环。

### 【面试题】：为什么说 `HashMap` 是线程不安全的？
- **【核心答案】**：
  * 并发写入时可能出现数据覆盖、数据丢失。
  * `size` 更新不是原子操作，统计结果可能不准确。
  * JDK 1.7 中扩容还可能导致链表成环，出现死循环。
- **【原理解析】**：`HashMap` 的 `put()`、`resize()`、链表插入、树化等过程都没有同步控制。多个线程同时写同一个桶时，可能基于旧状态分别做判断，最终后写覆盖前写。`size++` 也不是原子操作，多个线程同时修改会产生竞态条件，导致实际插入了多个元素，但 `size` 只增加一次。线程安全问题的根因，是内部状态更新没有建立互斥和可见性保障。
- **【面试扩展】**：只读场景下，如果 `HashMap` 已经构建完成并被安全发布，通常可以并发读；但只要存在并发写或读写混合，就不应该继续使用普通 `HashMap`。缓存、路由表、会话索引这类场景一般都要改用并发容器。
- **【一句话总结】**：`HashMap` 线程不安全的根因是内部状态变更完全没有并发控制。

### 【面试题】：`HashMap` 常见的遍历方式有哪些？哪种更推荐？
- **【核心答案】**：
  * 常见方式有 `entrySet()`、`keySet() + get()`、迭代器、`forEach`、`Stream` 和 `parallelStream`。
  * 同时需要 key 和 value 时，优先遍历 `entrySet()`。
  * `parallelStream` 不一定更快，非阻塞场景下往往更慢。
- **【原理解析】**：遍历 `entrySet()` 可以一次性拿到 key 和 value，避免 `keySet() + get()` 再做一次哈希查找，所以通常更高效。`parallelStream` 有线程调度、任务拆分、合并结果等额外开销，如果遍历逻辑非常轻量，开销可能比收益更大。只有在单次处理逻辑较重、存在明显阻塞或计算耗时时，并行化优势才更容易体现。
- **【面试扩展】**：如果只需要 key，可以遍历 `keySet()`；如果只需要 value，可以遍历 `values()`。开发里不要机械地把“并行流”当成性能优化手段，应先基准测试。
- **【一句话总结】**：遍历 `HashMap` 优先用 `entrySet()`，并行流快不快取决于业务负载而不是语法本身。

### 【面试题】：`ConcurrentHashMap` 和 `Hashtable` 有什么区别？
- **【核心答案】**：
  * 两者都能保证线程安全，但实现方式完全不同。
  * `Hashtable` 基本是整表级别的 `synchronized`，锁粒度粗，并发性能差。
  * JDK 1.7 的 `ConcurrentHashMap` 采用分段锁，JDK 1.8 采用 `CAS + synchronized`，锁粒度更细。
- **【原理解析】**：`Hashtable` 的同步方式比较直接，很多方法直接加 `synchronized`，导致线程即使访问不同桶位也容易互相阻塞。`ConcurrentHashMap` 的设计目标是尽量缩小锁范围，提高并发吞吐。JDK 1.8 中它和 `HashMap` 一样使用数组加链表/红黑树结构，但只在必要时锁住当前桶的头节点或树结构，同时配合 CAS 完成无锁初始化和部分更新。
- **【面试扩展】**：如果面试官问“为什么 `ConcurrentHashMap` 性能更高”，核心回答就是两点：锁粒度更细，读操作冲突更少。现代业务中，线程安全 Map 的主流选择几乎都是 `ConcurrentHashMap`。
- **【一句话总结】**：`Hashtable` 是粗粒度全表锁，`ConcurrentHashMap` 是高并发优化版线程安全哈希表。

### 【面试题】：`ConcurrentHashMap` 是怎么保证线程安全的？
- **【核心答案】**：
  * JDK 1.7 通过 `Segment + ReentrantLock` 保证线程安全。
  * JDK 1.8 取消 `Segment`，改用 `Node + CAS + synchronized`。
  * 读操作尽量无锁，写操作只锁局部桶位，整体并发度更高。
- **【原理解析】**：JDK 1.7 会把整个哈希表拆成多个 `Segment`，每个 `Segment` 都像一个小型 `HashMap`，写入某个段时只需获取该段的锁。JDK 1.8 彻底重构后，初始化桶数组、插入空桶等操作优先用 CAS；只有在链表或红黑树需要结构性修改时，才对当前桶的头节点加 `synchronized`。这种设计兼顾了线程安全和吞吐量。
- **【面试扩展】**：JDK 1.8 中如果桶内冲突严重，也会树化。红黑树节点由 `TreeBin` 包装，用状态位协调并发访问。这个点很适合在高级面试里体现源码理解深度。
- **【一句话总结】**：`ConcurrentHashMap` 的核心思想是能无锁就无锁，必须加锁时只锁最小范围。

### 【面试题】：JDK 1.7 和 JDK 1.8 的 `ConcurrentHashMap` 实现有什么不同？
- **【核心答案】**：
  * JDK 1.7 采用 `Segment` 分段锁。
  * JDK 1.8 取消 `Segment`，采用桶级别的 `CAS + synchronized`。
  * JDK 1.8 引入红黑树，在高冲突场景下性能更稳定。
- **【原理解析】**：JDK 1.7 的最大并发度主要受 `Segment` 个数限制，默认是 `16`。JDK 1.8 不再把并发能力绑定到固定段数量，而是细化到桶位甚至节点级别，在更多线程同时访问不同桶时能获得更高并发度。同时，JDK 1.8 的哈希冲突处理从单纯链表升级为链表加红黑树，改善了最坏情况下的性能退化。
- **【面试扩展】**：这题常和“为什么 JDK 1.8 不再用 `Segment`”连问。可以回答：分段锁灵活性不够、扩展性受限，而桶级并发控制更细，能更充分利用多核。
- **【一句话总结】**：JDK 1.8 的 `ConcurrentHashMap` 本质上是从段锁升级成了更细粒度的桶级并发控制。

### 【面试题】：为什么 `ConcurrentHashMap` 不允许 `key` 和 `value` 为 `null`？
- **【核心答案】**：
  * 主要是为了避免二义性。
  * `get(key)` 返回 `null` 时，无法区分“key 不存在”还是“value 本身就是 null”。
  * 并发场景下无法通过 `containsKey()` 再补一次判断来彻底消除歧义。
- **【原理解析】**：在普通 `HashMap` 中，如果 `get()` 返回 `null`，理论上还可以继续调用 `containsKey()` 判断 key 是否存在。但在并发容器里，这两个操作之间容器状态可能已经被其他线程改写，因此这个补充判断并不可靠。为了从语义层面彻底避免歧义，`ConcurrentHashMap` 干脆禁止 `null key` 和 `null value`。
- **【面试扩展】**：如果业务需要表达“空值”，通常会用一个特殊占位对象代替 `null`。这个设计也体现了并发编程里“宁可限制语义，也要保证语义清晰可判断”的原则。
- **【一句话总结】**：`ConcurrentHashMap` 禁止 `null`，本质上是为了避免并发环境下无法可靠判断键值是否存在。

### 【面试题】：`ConcurrentHashMap` 能保证复合操作的原子性吗？
- **【核心答案】**：
  * 不能，它保证的是单个操作线程安全，不保证多步业务逻辑天然原子。
  * 例如“先 `containsKey()` 再 `put()`”就是典型的非原子复合操作。
  * 要保证原子性，应优先使用 `putIfAbsent`、`computeIfAbsent`、`merge` 等原子方法。
- **【原理解析】**：线程安全不等于业务逻辑原子。像“先判断后执行”这种流程至少包含两个步骤，步骤之间可能被其他线程插入修改。例如线程 A 刚判断 key 不存在，线程 B 就先写入了值，线程 A 再继续 `put()`，结果就覆盖了线程 B 的写入。因此，单步安全和复合安全是两个层面的概念。
- **【面试扩展】**：在缓存击穿防护、幂等写入、计数聚合等场景下，经常要用 `computeIfAbsent` 或 `merge`。相比外部再加锁，这种方式更贴合 `ConcurrentHashMap` 的设计初衷，也更容易写出高并发代码。
- **【一句话总结】**：`ConcurrentHashMap` 保证的是单步安全，不保证“先判断再操作”这类多步逻辑天然原子。

### 【面试题】：`Collections` 工具类常见方法有哪些？使用时要注意什么？
- **【核心答案】**：
  * 常见能力有排序、查找替换、同步包装三类。
  * 排序相关如 `sort()`、`reverse()`、`shuffle()`、`swap()`、`rotate()`。
  * 查找替换如 `binarySearch()`、`max()`、`min()`、`fill()`、`frequency()`、`replaceAll()`。
  * 同步包装如 `synchronizedList()`、`synchronizedSet()`、`synchronizedMap()`。
- **【原理解析】**：`Collections` 本身不是集合容器，而是操作集合的工具类。它的 `synchronizedXxx()` 本质上是通过包装模式给原集合外面套一层同步控制，通常还是粗粒度锁。因此它能解决基本线程安全问题，但并发性能往往一般，不适合高并发核心链路。像 `binarySearch()` 这类方法还有使用前提，必须保证目标集合已经有序。
- **【面试扩展】**：这题很容易被追问“`Collections` 和 `Collection` 有什么区别”。一个是工具类，一个是单列集合顶层接口。开发中如果对并发性能有要求，应优先选 JUC 并发集合，而不是 `Collections.synchronizedXxx()`。
- **【一句话总结】**：`Collections` 是集合工具箱，不是集合体系本身；能做同步包装，但不是高并发场景的最优解。
